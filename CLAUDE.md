# Repository Guidelines

This is a Kratos multi-service monorepo. This file owns the layering
contract agents must follow when changing the template.

## Project structure

整仓是**一个** Go module（`module chatroom`），一个 `go.mod`，没有
`replace` 也没有 `go.work`。目录按官方 `go-kratos/beer-shop` 的思路分：

```
api/<domain>/service/     Contract package: proto sources + generated stubs
                           only, no implementation. One per business domain.
                           Callers depend on these, never on the implementing
                           service.
  v1/                      Proto + generated grpc/http stubs + openapi.yaml.

app/<domain>/service/     The microservices. Each is self-contained.
  cmd/server/              Entrypoint, Wire injector, main.go.
  configs/                 Runtime config (config.yaml). No secrets.
  internal/conf/           Config proto; generated by `make config`.
  internal/server/         HTTP/gRPC server wiring.
  internal/service/        Transport adapters; one file per resource.
  internal/biz/            Domain models, usecases, repo interfaces, errors.
  internal/data/           Repo implementations and storage clients.

third_party/              Third-party protos — ONE copy for the whole repo.
  google/api/             annotations.proto + http.proto (offline dependency).

pkg/                      Shared packages, imported by all services.
  keys/                   Redis keys and Pub/Sub channels — cross-service contract.
  errors/                 Framework-level error reasons (COMMON_*) — cross-service contract.
  middleware/             JWT, internal-token, and blacklist middleware.
  health/                 Health checks (liveness / readiness), shared semantics.
  breaker/                Circuit breaker for cross-service gRPC calls.
  dbpool/                 database/sql pool tuning and defaults.
  observability/          Metrics and tracing setup.
  nacos/                  Nacos client, registry, discovery, config source.
  testutil/               Test helpers (DB, Redis, JWT).
  tools/                  Build helpers (dev-env.mk, nacos-config.sh), not Go code.
```

`ws-gateway` has no `api/` counterpart — it is an aggregating gateway that
calls other services, it does not expose a business contract of its own.


## Layering & dependency rules

Three model shapes flow through three layers. `biz` owns the DO, `data`
owns the PO; `service` is a pass-through that converts at its boundary.

```
   client ──► DTO ──► service ──► DO ──► biz ──► DO ──► data ──► PO ──► storage
                                  ▲                ▲
                                  │ declares       │ implements
                                  └─── repo IF ────┘

   DTO  Data Transfer Object — proto request / response.
   DO   Domain Object        — pure biz model, no proto, no storage tags.
   PO   Persistent Object    — storage shape, owned by `data`.
```

| Layer   | Owns | Speaks at boundary | Never speaks            |
|---------|------|--------------------|-------------------------|
| service | —    | DTO ↔ DO          | PO, storage client      |
| biz     | DO   | DO                 | DTO, PO, storage client |
| data    | PO   | DO ↔ PO           | DTO                     |

- `service` imports the contract package (DTO) and `biz` (DO). Never `data`.
- `biz` imports the contract package only for error reason enums. Never
  `service`, never `data`. The repo interface declared here is the
  inversion seam.
- `data` imports `biz` to implement the repo interface. Never `service`,
  never DTOs.
- `cmd` is the only place that wires all layers via Wire.

Cross-cutting infrastructure (nacos, keys, errors, middleware,
observability, testutil) lives in `chatroom/pkg` — a shared package, not
a shared directory. Cross-service contracts must have exactly one
definition: two copies of a Redis key or an error reason string drift
silently. `pkg` never imports a service; the dependency direction is
one-way (service → pkg).

### Contract packages

Each business domain owns a contract package under `api/<domain>/service/`
(`chatroom/api/<domain>/service/v1`): proto sources plus generated stubs,
**no implementation**. The implementing service depends on its own contract
package; callers depend on the contract package, never on the service.

This is what makes independent evolution real. If callers depended on the
service package (the old layout), every internal refactor of the service —
swapping an ORM, splitting a package — would ripple into the callers'
builds. With a contract package, the only edge on the dependency graph is
"service → contract", and a contract that does not change does not force
a recompile of the caller.

Dependency direction:

```
service  →  contract  →  (nothing)
service  →  pkg       →  (nothing)
```

Contract packages never depend on each other (no domain proto imports
another domain's proto). `pkg` never depends on a contract.

Never import a service package from another service. `internal/` already
blocks the obvious cases at compile time; the contract package removes the
temptation for the legal ones.

Splitting a domain out into its own repository later is a version-number
change, not a restructure — the import paths and dependency arrows stay
the same.

A change crossing these arrows the wrong way is a layering bug; fix the
design rather than add the import.

### Protobuf global registry

protobuf's descriptor registry is **process-global**, and the whole repo
is one module — several domains' generated code can end up linked into the
same binary (test binaries especially). The registry keys files by their
path *relative to the protoc `--proto_path` root*, so two protos with the
same relative path collide at `init()` with
`proto: file "v1/error_reason.proto" is already registered`.

Both generation scripts therefore run protoc **from the repo root** with a
root that includes the domain:

| Script             | `--proto_path` | Registered path                             |
|--------------------|----------------|---------------------------------------------|
| `api/gen.sh`       | `api`          | `<domain>/service/v1/<file>.proto`          |
| `app/gen-conf.sh`  | `app`          | `<service>/service/internal/conf/conf.proto`|

Never point either script at a narrower root — that collapses every
domain onto the same relative path again.

### Cross-service degradation contract

Remote clients live in the caller's `data` layer (`remote_<svc>.go`).
When a downstream is unreachable, unconfigured, or missing its internal
token, they must return an **error** — never an empty list or slice.

This matters because several endpoints infer "the user does not exist"
from "the user was not returned". An empty result on a degraded call is
indistinguishable from a genuinely missing user, so a downstream outage
turns into a misleading `USER_NOT_FOUND` rejection instead of a
degraded-but-working path.

- Downstream unavailable → error → the caller decides: existence checks
  fail **open** (block normal business is worse than admitting a ghost
  member), profile lookups log a warning and return the list without
  nicknames.
- A genuinely missing user → an explicit "missing" list → reject.
- Batch endpoints truncate silently past their per-request id cap
  (the user service caps at 200). Chunk the ids on the caller side, or
  the truncated tail is reported as "does not exist".
- A failing chunk fails the whole batch. A partial result is worse than
  an error: the caller cannot tell "absent" from "not fetched".

### Circuit breaker contract

Cross-service gRPC clients are wrapped with `pkg/breaker` — the breaker
middleware must sit **innermost** in the client middleware chain, right
next to the RPC call:

```go
grpc.WithMiddleware(
    authForwarding(),
    internalForwarding(),
    oteltrace.Client(),
    breaker.Client(),   // innermost
)
```

Innermost on purpose: a request rejected by the breaker still passes
through the tracing middleware, so the rejection shows up in traces. One
level out and the symptom is "the upstream suddenly errors everywhere but
no trace explains it".

- Only 5xx (500 / 503 / 504) counts as a failure. A 404 "user does not
  exist" is a business result, not an unhealthy downstream.
- The built-in Kratos SRE breaker is **not** used: its window is 3s and it
  requires 20 requests in the window before evaluating. At 5 QPS a service
  never reaches 20 requests in 3s, so the breaker would never trip.
  `pkg/breaker` uses a 10s window and treats "too few samples" as
  "do not trip".
- A rejected request surfaces to the caller as an **error**, which the
  degradation contract above already handles: it must never be flattened
  into an empty result.

### Config file contract (bootstrap vs config)

Every service reads **two** files, and both must exist:

| File | Contains | Never contains |
|------|----------|-----------------|
| `configs/bootstrap.yaml` | only `registry.nacos` | business parameters |
| `configs/config.yaml` | business parameters | `registry` |

The split breaks a circular dependency: the business config in the config
center depends on "which nacos to connect to", so that fact cannot live in
the config center. `bootstrap.yaml` is read **first** (file + env only) to
build the nacos client; the business config is then merged from
file + nacos + env, lowest to highest priority.

**Both files are mandatory.** `cmd/server/main.go` loads the bootstrap
first and `panic`s if it is missing — kratos' file source does an
`os.Stat`, so a missing file is a hard error, not an empty config:

```
panic: stat configs/bootstrap.yaml: no such file or directory
```

The `bootstrap.yaml` `service_name` must be `<service>`-specific
(`chatroom-user`, `chatroom-friend`, …) — it is what other services
discover this one by. Copying another service's file verbatim registers
this process under the wrong name.

### Database pool contract

Every service that owns a database sets the pool explicitly in
`data.database` (`max_open_conns`, `max_idle_conns`, `conn_max_lifetime`,
`conn_max_idle_time`). `database/sql` defaults are unsafe in production:
`MaxOpenConns` defaults to unlimited and `ConnMaxLifetime` to "never
recycle" — the latter shows up as sporadic 500s after a MySQL proxy
restart.

`pkg/dbpool` applies the values and falls back to defaults for `<= 0` and
negative input, so a misconfigured `0` cannot turn into an unlimited pool.

Durations in the YAML config use the **proto** format (`1800s`), not
`30m` — protojson only accepts s/ms/us/ns. Bools cannot be supplied via
`${VAR}` placeholders either: protojson rejects the string form.

Connection budget is **shared across all services**: 5 services × up to 10
replicas × 10 connections = 500. Size MySQL's `max_connections` above
that; the default 151 is not enough.

### Observability contract

Metrics and tracing are off by default and enabled by environment
variables (`METRICS_ADDR`, `OTEL_EXPORTER_OTLP_ENDPOINT`). An empty value
means "off" — not "use a default address" — because the five services run
side by side locally and would collide on a default port.

The exporter wiring lives in `chatroom/pkg/observability`; services only
translate their own config into `pkg/observability.Config`
(`internal/observability/`). The metrics port in containers is 9100 and
is declared in three places that must stay in sync: the ConfigMap
(`METRICS_ADDR`), the container port, and the Prometheus pod annotations.

### Health check contract

Every service exposes two endpoints, both registered with `srv.Handle`
(which bypasses the Kratos middleware chain — probes carry no token, so
the JWT middleware would reject them with 401):

- `/healthz` — **liveness**. Reports that the process is alive and
  touches **no dependency**. A dependency outage must never fail
  liveness: restarting the pod cannot fix a downed MySQL, it only turns
  a degradation into a CrashLoopBackOff with a larger blast radius.
- `/readyz` — **readiness**. Probes the dependencies and returns 503
  when a **hard** dependency is down, so K8s drops the pod from the
  Service endpoints.

The shared implementation lives in `chatroom/pkg/health`; each service
declares its own dependencies in `internal/data/health.go`:

```go
c.Add("mysql", true, d.PingMySQL)   // hard
c.Add("redis", false, d.PingRedis)  // soft
```

Hard vs soft is decided by one question: **if this dependency is down,
can the service still answer requests correctly?**

- Hard → readiness returns 503 (pod leaves the endpoints).
- Soft → readiness stays 200 with status `degraded`.
- MySQL is **hard** for user / friend / conversation / message: without
  it nothing can be read or written.
- Redis is **soft** for those four: rate limiting, blacklists, caches
  and broadcasts all fail open. Marking it hard would evict every pod
  of every service on a Redis blip — a far larger blast radius than the
  degradation itself.
- Redis is **hard** for ws-gateway: Pub/Sub is the only channel that
  delivers messages to WS clients. Accepting new connections with a dead
  subscription just makes clients wait forever for messages that can
  never arrive. Fast failure is better.

The classification is guarded by tests
(`<service>/internal/data/health_test.go`) — flipping Redis to hard is
a regression, not a tweak.

Probes in the manifests: `readinessProbe` → `/readyz`,
`livenessProbe` and `startupProbe` → `/healthz`. The probe
`timeoutSeconds` must exceed the per-check timeout in `pkg/health`
(2s), otherwise the probe gives up while the server is still probing.

### Layer responsibilities

**service (DTO ↔ DO)**

- `convert<Resource>` parses an incoming proto into a DO. The reverse
  direction is built inline at the return site; the reply type is
  whatever the proto declares — usually the resource itself
  (`return &v1.<Resource>{...}, nil`), sometimes a list wrapper
  (`*v1.<Resources>Set`), or `&emptypb.Empty{}` for deletes. Inlining
  keeps each handler self-contained.
- Embed `Unimplemented<Resource>ServiceServer`.
- Parse AIP list requests via `filtering` / `ordering` / `pagination`;
  apply `fieldmask.Update` for partial updates.
- Validate request inputs at the service boundary before delegating to the
  usecase.
- Return `biz` errors. No business rules, no storage access, no PO.

**biz (DO only)**

- Owns the DO (`type <Resource> struct` — no proto, no storage tags),
  the usecase, and the repo interface (`type <Resource>Repo interface`).
- Owns typed errors built with `errors.NotFound` / `errors.BadRequest`
  plus the API error reason enum.
- Owns `ListOption` helpers — `ListFilter`, `ListOrderBy`, `ListOffset`,
  `ListLimit` — so callers compose queries without leaking storage
  primitives.

**data (DO ↔ PO)**

- _Repo shape_: implement `biz.<Resource>Repo`. The constructor returns
  the interface, never the concrete type:
  `func New<Resource>Repo(d *Data) biz.<Resource>Repo`.
- _PO and conversion_: define a PO when the storage shape diverges from
  the DO. PO types stay inside `data`. Use free functions
  `new<Resource>` (DO → PO, write) and `toBiz` (PO → DO, read).
  Driver-specific builder types never leave `data`.
- _Shared clients_: `*Data` (declared in `internal/data/data.go`) holds
  long-lived storage clients. Repos receive `*Data` and never construct
  their own clients.
- _Querying_: translate `ListOptions.Filter` and `ListOptions.OrderBy`
  into the storage driver's query language inside the repo.
- _Errors_: map driver errors to `biz` typed errors so callers above
  never branch on the driver.

**server**

- Construct HTTP/gRPC servers, apply middleware, register services. No
  translation, no business logic.

### Add-a-resource checklist

1. **DTO**: define `Create<Resource>` / `Get<Resource>` /
   `List<Resources>` / `Update<Resource>` / `Delete<Resource>` in the
   domain's contract package (`api/<domain>/service/v1/`), then `make api`
   (or `make api` inside that contract directory).
2. **DO + repo interface**: declare both in `biz`; build the usecase on
   top of the interface.
3. **Repo impl**: implement in `data` returning `biz.<Resource>Repo`;
   add a PO and the matching conversion helpers when storage shape
   diverges from DO.
4. **Wiring**: register the repo constructor in `data.ProviderSet`, the
   usecase in `biz.ProviderSet`, the service in `service.ProviderSet`;
   register HTTP/gRPC services in `internal/server`.
5. **Regenerate**: `make all` to refresh Wire and `go.mod`.

### Testing seam

Tests live beside the code they cover (`*_test.go`). Test layers in
isolation: service tests fake the usecase, biz tests fake the repo, data
tests exercise repo implementations at the storage boundary.

## Generation & generated files

Regenerate via `make api`, `make config`, or `make all`; never hand-edit
`*.pb.go`, `*_grpc.pb.go`, `*_http.pb.go`, or `wire_gen.go`.

- Contract protos are generated with **protoc**, not buf (`cd api/<domain>/service
  && make api`, which calls `api/gen.sh`). Contracts import
  `third_party/google/api/annotations.proto` from the repo root, and buf v2's
  module root is a single directory — cross-directory references are rejected
  (`is outside the context directory`), while `deps:` only takes registry
  names. protoc supports multiple `--proto_path`, the same approach the
  official `go-kratos/beer-shop` uses. Plugin versions are pinned with
  `@version` in `api/gen.sh`; build output is cached under
  `.cache/protoc-plugins/` keyed by the version set.
- Config protos are generated with **protoc** too (`cd app/<service>/service
  && make config`, which calls `app/gen-conf.sh`). Both scripts run protoc
  from the repo root so the registered proto path carries the domain (or
  service) name — see "Protobuf global registry" above for why that is
  mandatory.
- `make api` lives in the **contract** package directory
  (`api/<domain>/service/`), not in the service directory.
- The repo-root `Makefile` aggregates: `api` / `build` / `test` / `vet` /
  `config` / `proto` / `wire` / `all` across every service and contract.
- The kratos CLI (`kratos proto server`) runs **inside the service directory**
  and points at the contract proto path — three levels up from
  `app/<service>/service/`, so
  `kratos proto server ../../../api/<domain>/service/v1/<domain>.proto`.
  It writes the `internal/service/<domain>.go` skeleton (only when the file
  does not already exist).

## Naming & error reasons

- Resource: `<Resource>` (e.g., `Todo`); collection RPC:
  `List<Resources>`.
- Types: repo `<Resource>Repo`, usecase `<Resource>Usecase`, service
  `<Resource>Service`. PO types live inside `internal/data/`; pick a
  name that fits the storage driver and convert with
  `new<Resource>(do)` / `toBiz(po)` free functions.
- Error reasons: declared in the contract package at
  `api/<domain>/service/v1/error_reason.proto`, surfaced as
  `Err<Resource><Cause>` in `biz`.

## Commits & security

- Conventional Commits: `feat:`, `fix:`, `refactor:`, `chore(deps):`,
  `docs:`, `test:`. Regenerated files belong in the same commit as
  their source.
- Never commit real credentials in `configs/config.yaml`.
